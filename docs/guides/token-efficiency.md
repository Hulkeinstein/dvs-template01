## 개요

### Claude Code란?
Claude Code는 Anthropic의 Claude 3.5 Sonnet 모델을 기반으로 하는 개발 도구입니다. 200,000 토큰의 Context Window를 가지고 있으며, 이는 장편 소설 1권 분량에 해당합니다.

### 왜 토큰 관리가 중요한가?

#### 1. 대화 수명 연장
```
메모리 최적화 전: 20-30회 대화 후 Context 초과
메모리 최적화 후: 50-70회 대화 가능
```

#### 2. 정보 손실 방지
Context가 과도하게 차면 "Lost in the Middle" 현상 발생:
- 중간 부분의 정보를 놓침
- 중요한 디테일 누락
- 일관성 없는 응답

#### 3. 응답 품질 향상
```
적은 Context: 빠른 응답, 정확한 참조
많은 Context: 느린 응답, 모호한 참조
```

#### 4. 비용 효율성
토큰 사용량이 많을수록:
- 응답 시간 증가
- 에러 발생 가능성 증가
- 세션 자동 재시작 빈도 증가

## Context Window 구조

### 200,000 토큰의 구성

Claude Code의 Context Window는 다음과 같이 구성됩니다:

```
200,000 토큰 (전체)
│
├─ System Instructions (~5,000 토큰)
│  └─ Claude Code의 기본 동작 규칙, 도구 사용법
│
├─ Memory Files (~10,000-80,000 토큰) ⚠️
│  ├─ ~/.claude/CLAUDE.md (개인 메모리)
│  │  ├─ modules/memory-guide.md
│  │  ├─ modules/coding-principles.md
│  │  └─ modules/...
│  │
│  └─ ./CLAUDE.md (프로젝트 메모리)
│     ├─ DEVELOPMENT_PLAN.md
│     ├─ modules/architecture.md
│     ├─ modules/workflow.md
│     └─ modules/... (import된 모든 파일)
│
├─ 대화 히스토리 (누적)
│  ├─ User: 이전 프롬프트 1
│  ├─ Assistant: 이전 응답 1
│  ├─ Tool Results: 파일 읽기 결과
│  ├─ User: 이전 프롬프트 2
│  ├─ Assistant: 이전 응답 2
│  └─ ... 계속 누적
│
└─ 현재 User 프롬프트 및 응답
```

### 입력 순서

Claude Code는 다음 순서로 정보를 로드합니다:

```
1. System Instructions (고정)
2. Memory Files (매 프롬프트마다 로드)
3. 대화 히스토리 (누적)
4. 사용자의 새 프롬프트
```

**중요**: Memory Files는 **매 프롬프트마다** 로드됩니다!

### 토큰 계산법

#### 한국어
```
1 토큰 ≈ 2자

예시:
"안녕하세요" (5자) = 약 2.5 토큰
"Claude Code는 훌륭한 도구입니다" (20자) = 약 10 토큰
```

#### 영어
```
1 토큰 ≈ 4자 (또는 0.75 단어)

예시:
"Hello World" (11자) = 약 2.75 토큰
"Claude Code is an excellent tool" (32자) = 약 8 토큰
```

#### 코드 (TypeScript/JavaScript)
```
1 토큰 ≈ 3-4자

예시 (한 줄):
"const message = 'Hello World';" (31자) = 약 8-10 토큰
```

#### 실제 파일 예시

**300줄 React 컴포넌트**:
```
평균 60자/줄
300줄 × 60자 = 18,000자
18,000자 ÷ 3자/토큰 = 약 6,000 토큰
```

**1,000줄 문서**:
```
평균 50자/줄 (한영 혼합)
1,000줄 × 50자 = 50,000자
50,000자 ÷ 3자/토큰 = 약 16,700 토큰
```

### 실제 크기 비교

#### 111,000 토큰은 얼마나 큰가?

**텍스트 양**:
- A4 용지: 약 111장 (한 장당 2,000자 기준)
- 장편 소설: 약 1권 (300페이지 기준)
- 블로그 포스트: 약 70-80개

**코드 파일**:
- TypeScript 컴포넌트 (300줄): 약 18-20개
- 중간 규모 Feature 전체 파일

**대화 기준**:
- 긴 대화: 50-70회 왕복
- 중간 대화: 100-150회 왕복
- 짧은 대화: 200-300회 왕복

## 메모리 최적화 전략

### 적정 메모리 크기

#### 업계 권장사항
```
메모리 파일 크기: 5,000-20,000 토큰
└─ 전체 Context의 2.5-10%
```

#### 크기별 영향

| 메모리 크기 | 전체 비율 | 평가 | 문제점 |
|------------|----------|------|--------|
| 5K-20K | 2.5-10% | ✅ 이상적 | 없음 |
| 20K-40K | 10-20% | ⚠️ 주의 | 작업 공간 부족 가능 |
| 40K-80K | 20-40% | ❌ 과다 | Lost in the Middle 위험 |
| 80K+ | 40%+ | 🚫 위험 | 심각한 성능 저하 |

### Lost in the Middle 문제

#### 무엇인가?
AI 모델은 긴 Context에서:
- **시작 부분**: 잘 기억 ✅
- **중간 부분**: 놓치기 쉬움 ⚠️
- **끝 부분**: 잘 기억 ✅

#### 예시
```
[Memory Files: 80,000 토큰]
├─ 첫 10,000 토큰 → 잘 참조
├─ 중간 60,000 토큰 → 일부 누락 위험
└─ 마지막 10,000 토큰 → 잘 참조
```

#### 해결책
1. **메모리 크기 줄이기**: 핵심 내용만 유지
2. **중요한 정보는 끝에**: 최근 추가된 파일일수록 잘 참조
3. **명시적 참조**: "memory-guide.md의 'Be specific' 원칙" 같이 구체적으로 지정

### Import 관리 전략

#### 1. 항상 Import (핵심 메모리)
```markdown
# CLAUDE.md
- @./modules/architecture.md      # 프로젝트 구조 (필수)
- @./modules/workflow.md          # 워크플로우 허브 (필수)
```

**기준**:
- 모든 작업에 필요한 정보
- 자주 참조하는 규칙
- 크기: 각 파일 3,000-5,000 토큰 이하

#### 2. 선택적 Import (참고 문서)
```markdown
# 참고용 - Import 하지 않음
- docs/guides/token-efficiency.md
- modules/database-schema-reference.md
- modules/production-deployment.md
```

**기준**:
- 특정 작업에만 필요
- 크기가 큰 문서 (5,000 토큰 이상)
- 읽기 전용 참고 자료

#### 3. Import 제거 판단
다음 경우 Import 제거 고려:
- 최근 3개월간 참조 안 함
- 파일 크기 5,000 토큰 초과
- 특정 시나리오에만 필요 (배포, 마이그레이션 등)

### 메모리 파일 작성 원칙

#### 1. "Be Specific" 원칙
```markdown
❌ 나쁜 예:
코드를 잘 작성하세요.

✅ 좋은 예:
Use 2-space indentation for TypeScript.
```

#### 2. 간결성
```markdown
❌ 나쁜 예 (100줄):
이 프로젝트는 Next.js를 사용합니다.
Next.js는 React 기반의 프레임워크로...
[긴 설명]

✅ 좋은 예 (10줄):
## Tech Stack
- Next.js 14 (App Router)
- TypeScript (strict mode)
- Supabase (Database)
```

#### 3. 구조화
```markdown
# 제목

## 섹션 1
- 불릿 포인트
- 명령어: `git commit -m "feat: add feature"`

## 섹션 2
```bash
코드 블록은 멀티라인만
```
```

#### 4. 중복 제거
```markdown
❌ 나쁜 예:
# git-workflow.md
브랜치 생성: git checkout -b feature/name

# development-guide.md
브랜치 생성: git checkout -b feature/name

✅ 좋은 예:
# git-workflow.md (단일 소스)
브랜치 생성: git checkout -b feature/name

# development-guide.md
브랜치 생성: @./workflow/git-workflow.md 참조
```

### 최적화 프로세스

#### Step 1: 현재 상태 파악
```bash
# 메모리 파일 줄 수 확인
find modules -name "*.md" -exec wc -l {} + | tail -1
```

#### Step 2: 큰 파일 식별
```bash
# 300줄 이상 파일 찾기
find modules -name "*.md" -exec wc -l {} + | awk '$1 > 300'
```

#### Step 3: 우선순위 결정
1. 500줄 이상 파일 → 최우선 축약
2. 자주 참조 안 하는 파일 → Import 제거
3. 중복 내용 → 통합 또는 제거

#### Step 4: 실행
```bash
# Before
modules/production-deployment.md (500줄, 8,500 토큰)

# After (50% 축약)
modules/production-deployment.md (250줄, 4,250 토큰)

# 절약: 4,250 토큰
```

## /clear 사용 가이드

### /clear란?

`/clear` 명령어는 현재 대화 히스토리를 모두 삭제하고 새로운 세션을 시작합니다.

```
Before /clear:
├─ Memory Files (유지)
├─ 대화 히스토리 (삭제 대상)
└─ Tool Results (삭제 대상)

After /clear:
├─ Memory Files (유지)
└─ [새로운 대화 시작]
```

**중요**: Memory Files는 삭제되지 않고 유지됩니다!

### 언제 사용해야 하는가

#### 시나리오 1: 완전히 새로운 작업 시작
```
작업 A 완료 (북마크 시스템 개발)
├─ 파일 5개 읽음
├─ 대화 30회
├─ 사용: 40,000 토큰
└─ 커밋 완료

→ /clear

작업 B 시작 (결제 시스템 개발)
└─ 깨끗한 상태로 시작
```

**판단 기준**:
- 이전 작업의 컨텍스트가 전혀 필요 없음
- 완전히 다른 Feature
- Context 공간 확보 필요

#### 시나리오 2: Context 한계 도달
```
현재 사용: 180,000 / 200,000 토큰
남은 공간: 20,000 토큰

→ /clear

새로운 시작: 0 / 200,000 토큰
남은 공간: ~110,000 토큰 (메모리 제외)
```

**판단 기준**:
- 사용량이 90% 초과
- 응답이 느려지거나 이상함
- Claude가 "context가 부족합니다" 언급

#### 시나리오 3: 대화가 산만해짐
```
대화 흐름:
- 북마크 시스템 논의
- 중간에 스타일 이슈 디버깅
- 다시 결제 시스템 논의
- 데이터베이스 스키마 논의
- ...혼선 발생

→ /clear

새 출발:
- 명확한 목표 설정
- 집중된 대화
```

**판단 기준**:
- 여러 주제를 동시에 다룸
- Claude가 이전 컨텍스트와 혼동
- 응답이 일관성 없음

### 언제 사용하지 말아야 하는가

#### 시나리오 1: 연속된 작업 중
```
❌ 나쁜 예:
파일 A 수정 중
│
├─ 파일 읽기
├─ 수정 계획
└─ /clear ← 여기서 하면 안 됨!
    └─ 이전 논의 내용 모두 잊음

✅ 좋은 예:
파일 A 수정 중
│
├─ 파일 읽기
├─ 수정 계획
├─ 구현
├─ 테스트
└─ 커밋
    └─ /clear ← 완료 후 사용
```

#### 시나리오 2: 복잡한 컨텍스트 필요
```
❌ 나쁜 예:
여러 파일 분석 중
│
├─ 파일 A, B, C 읽음 (20,000 토큰)
├─ 문제 파악
└─ /clear ← 다시 파일 읽어야 함 (비효율)

✅ 좋은 예:
여러 파일 분석 중
│
├─ 파일 A, B, C 읽음
├─ 문제 파악
├─ 수정 완료
└─ /clear ← 작업 완료 후
```

#### 시나리오 3: 에러 디버깅 중
```
❌ 나쁜 예:
에러 디버깅
│
├─ 시도 1 실패
├─ 시도 2 실패
└─ /clear ← 이전 시도 기록 사라짐

✅ 좋은 예:
에러 디버깅
│
├─ 시도 1 실패 (원인: X)
├─ 시도 2 실패 (원인: Y)
├─ 시도 3 성공 (해결: Z)
└─ /clear ← 해결 후
```

### 전략적 타이밍

#### Feature 단위
```
Feature 1 시작
├─ 설계
├─ 구현
├─ 테스트
└─ 커밋
    └─ /clear ← 여기서!
        └─ Feature 2 시작
```

#### 일일 작업 구분
```
오전 작업 (3-4시간)
├─ Feature A 구현
└─ Feature A 완료
    └─ /clear
        └─ 오후 작업 시작
```

#### 복잡도 기준
```
간단한 작업 (1-2시간): /clear 불필요
중간 작업 (3-4시간): 완료 후 /clear
복잡한 작업 (4시간+): 중간에 체크포인트 + /clear
```

## 작업 분할 전략

### 최적 작업 단위

#### 권장 크기: 20,000-40,000 토큰
```
이 범위에서:
✅ 거의 모든 정보 기억
✅ 빠른 응답 속도
✅ 정확한 참조
✅ 일관된 품질
```

#### 작업 단위별 적정 범위

| 작업 규모 | 토큰 사용 | 파일 읽기 | 대화 횟수 | 예시 |
|----------|----------|----------|----------|------|
| **Small** | 5K-15K | 1-3개 | 5-10회 | 버그 수정, 스타일 조정 |
| **Medium** | 15K-40K | 3-7개 | 10-25회 | 컴포넌트 추가, API 통합 |
| **Large** | 40K-80K | 7-15개 | 25-50회 | Feature 개발, 리팩토링 |
| **X-Large** | 80K+ | 15개+ | 50회+ | **분할 필요** |

### 작업 분할 방법

#### 큰 작업을 어떻게 나눌까?

**나쁜 예** (X-Large, 분할 안 함):
```
전체 인증 시스템 리팩토링
├─ OAuth 구조 변경
├─ 비밀번호 인증 추가
├─ 세션 관리 개선
├─ 보안 강화
├─ 테스트 작성
└─ 문서 업데이트
총 100,000 토큰 예상 ❌
```

**좋은 예** (분할):
```
Phase 1: OAuth 구조 변경 (30K 토큰)
├─ 설계 검토
├─ 코드 수정
└─ 기본 테스트
    └─ 커밋 + /clear

Phase 2: 비밀번호 인증 추가 (35K 토큰)
├─ DB 스키마 추가
├─ Server Actions 구현
└─ UI 컴포넌트
    └─ 커밋 + /clear

Phase 3: 세션 관리 + 보안 (30K 토큰)
└─ ... (계속)
```

#### 분할 기준

**1. 기능 단위**
```
결제 시스템 개발
├─ Phase 1: 데이터베이스 설계
├─ Phase 2: Backend API
├─ Phase 3: Frontend UI
└─ Phase 4: 테스트 & 검증
```

**2. 파일 그룹**
```
컴포넌트 리팩토링
├─ Group 1: Header 관련 (5개 파일)
├─ Group 2: Footer 관련 (4개 파일)
└─ Group 3: Sidebar 관련 (6개 파일)
```

**3. 복잡도 순서**
```
인증 시스템
├─ Step 1: 간단한 부분 (OAuth 토큰 갱신)

## 토큰 사용량 확인 방법

### 직접 확인의 한계

**안타깝게도**: Claude Code에는 토큰 사용량을 직접 확인할 수 있는 방법이 없습니다.

**존재하지 않는 것들**:
- `/tokens` 명령어 ❌
- UI의 토큰 카운터 ❌
- 실시간 토큰 모니터 ❌

### 간접적인 신호

#### 신호 1: 자동 요약 메시지
```
"This session is being continued from a previous
conversation that ran out of context.
The conversation is summarized below:"
```
→ 200,000 토큰에 근접했다는 의미

#### 신호 2: 응답 품질 저하
- 이전 내용을 잘 기억하지 못함
- 일관성 없는 응답
- 중요한 디테일 누락
→ Context가 과부하 상태

#### 신호 3: 응답 시간 증가
- 평소보다 느린 응답
- 답변 생성 중 멈춤
→ Context 처리에 시간 소요

#### 신호 4: Claude의 명시적 언급
```
"Context가 많이 사용되었습니다"
"/clear를 고려해보세요"
"이전 대화 내용이 많아 요약하겠습니다"
```

### 예상 계산 방법

#### 메모리 파일
```bash
# 줄 수 확인
find modules -name "*.md" -exec wc -l {} +

# 토큰 예상 (줄당 17토큰 평균)

```

#### 대화 히스토리
```
간단한 대화 (1회):

Claude 응답: 500자 = 250 토큰
소계: 6,275 토큰
```

```

10회 대화 후 (파일 읽기 없음):

└─ 남음: 117,090 토큰

```

```

## 트러블슈팅

### 문제 1: Context 부족 징후

#### 증상
- "이전 대화를 찾을 수 없습니다"
- 방금 전 내용을 잊음
- 일관성 없는 응답
- 자동 요약 메시지 출현

#### 해결책
```
즉시:
1. /clear 실행
2. 중요 정보 다시 제공
3. 작업 재개

장기:
1. 메모리 파일 최적화
2. 작업 단위 축소
3. 정기적인 /clear
```

### 문제 2: 응답이 이상함

#### 증상
- Lost in the Middle: 중간 정보 누락
- 모순된 답변
- 불완전한 코드
- 잘못된 파일 참조

#### 진단
```
원인 1: Context 과부하
└─ 해결: /clear

원인 2: 모호한 참조
└─ 해결: 명시적 참조 ("file.ts의 Line 42")

원인 3: 여러 주제 혼재
└─ 해결: 작업 명확히 구분
```

#### 해결책
```
1. /clear 후 재시작
2. 구체적인 질문으로 다시
3. 파일 경로와 줄 번호 명시
4. 한 번에 하나의 주제만
```

### 문제 3: 긴 작업 처리

#### 상황
```
작업: 전체 인증 시스템 개선
예상 시간: 6-8시간
예상 토큰: 150,000+
```

#### 잘못된 접근
```
❌ 한 세션에 모두:
├─ 메모리: 80,000
├─ 작업: 70,000+
└─ 총: 150,000+ ← 거의 한계
```

#### 올바른 접근
```

Phase 1: 설계 (2시간, 40K 토큰)
└─ /clear

Phase 2: OAuth 개선 (2시간, 35K 토큰)

- [ ] 필요한 Memory 파일 확인
- [ ] 추가로 읽을 문서 식별
- [ ] 명시적 참조 표현 준비

### Context 관리 체크리스트

#### 대화 중
- [ ] 20,000-40,000 토큰 단위로 작업
- [ ] 구체적 파일 경로로 참조
- [ ] 응답 품질 모니터링
- [ ] 이상 징후 발견 시 즉시 /clear

#### 작업 완료 시
- [ ] 커밋 완료 확인
- [ ] 다음 작업 계획 확인
- [ ] 새 작업이면 /clear 실행
- [ ] 연속 작업이면 /clear 보류

#### 세션 종료 전
- [ ] 중요 내용 Memory에 기록 (필요시)
- [ ] 다음 작업 TODO 정리
- [ ] /clear 실행 (다음 시작 시 깨끗한 상태)

## 결론

### 핵심 원칙

1. **메모리는 최소한으로**: 20,000-30,000 토큰 목표
2. **작업은 작게**: 20,000-40,000 토큰 단위
3. **/clear는 전략적으로**: 작업 전환 시점
4. **명시적 참조**: 구체적인 파일명과 위치
5. **정기적 최적화**: 분기별 메모리 감사

### 실천 가이드

```
일상 작업:
1. 작업 시작 → Context 확인
2. 20-40K 단위로 진행
3. 작업 완료 → 커밋
4. 새 작업 시작 → /clear

주간 루틴:
- 메모리 파일 리뷰
- 큰 파일 축약
- 사용하지 않는 Import 제거

분기 루틴:
- 전체 메모리 감사
- 최적화 실행
- 새로운 패턴 반영
```

### 기대 효과

```
최적화 전:
- 20-30회 대화 후 Context 초과
- 중간 내용 자주 놓침
- 응답 속도 느림

최적화 후:
- 50-70회 대화 가능
- 정확한 정보 참조
- 빠른 응답
- 일관된 품질
```
