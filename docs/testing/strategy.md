# 테스트 전략 가이드

실용적 테스트 전략: 우선순위와 ROI 기반 접근

## 1) 테스트 우선순위

1. **에러 처리 (필수 필드/잘못된 타입/변환 실패)**: 최우선. 데이터 맵퍼의 핵심 역할. 실패를 명확하게 처리하는지 검증.
2. **금액 로직 (가격/세금/반올림/통화 단위)**: 두 번째. 정확성이 필수. 부동소수점 오차 방지를 위해 `decimal.js` 같은 고정소수 라이브러리 사용 권장.
3. **엣지 케이스 (빈 문자열/null/undefined/특수문자/날짜 파싱 실패)**: 세 번째. 에러 처리와 함께 "입력 정규화 계약"을 명확히 정의.
4. **통합 테스트 (스키마, Supabase 타입 호환)**: 네 번째. 실제 DB 연결은 필수 경로만 최소화. 나머지는 계약 테스트로 대체.
5. **성능 테스트**: 다섯 번째. 단위 테스트와 분리. 대용량 데이터 변환 시간 측정은 별도 스위트로. 매 PR마다 실행하지 않음.
6. **스냅샷 테스트**: 최하위. 구조가 자주 변경되는 경우 취약. 불변 스키마의 복잡한 결과에만 제한적 사용.

## 2) 설계 관점 권장사항

### 런타임 스키마 검증
TypeScript 타입만으로는 런타임 에러를 방지할 수 없음. `zod` 또는 `valibot`으로 입력 스키마 정의 및 검증. 테스트는 "스키마 통과/실패"를 기준으로 작성.

### 프로퍼티 기반 테스트
태그에 임의 유니코드, 공백/구두점 혼합, 랜덤 금액/세율로 "불변식(invariants)" 검증. 예: "출력 합계는 항목 합의 합"과 같은 규칙을 퍼즈 테스트로 보장.

### 계약 테스트 (Contract Test)
"맵퍼 출력 ↔ DB 스키마" 간 계약을 샘플 스키마로 검증. 실제 DB 없이도 스키마 변경을 조기 탐지 가능.

### 시간 의존성 통제
날짜 파싱/타임존 로직이 있으면 `fakeTimers`로 시간을 고정. 테스트 환경의 로컬 타임존 변화에 영향받지 않도록 방지.

### 테스트 데이터 빌더
매 케이스마다 객체를 수동 생성하지 말고 빌더 패턴으로 가독성과 재사용성 확보.

## 3) 안정적인 테스트 작성 규칙

- 구현 세부사항에 의존 금지. "정렬 방식"이 요구사항이 아니면 `toContainEqual` 또는 `expect.arrayContaining` 사용.
- 에러 메시지는 "에러 코드/에러 종류"를 검증. 전체 텍스트 일치는 피함.
- 스냅샷은 "스키마 안정 + 사람이 검토할 가치가 있는 구조"에만 사용. 나머지는 명시적 어서션으로.

## 4) 파일 구성 제안

```
__tests__/
  unit/
    utils/
      courseDataMapper.success.test.ts     // 정상 케이스 + 금액/반올림 규칙
      courseDataMapper.errors.test.ts      // 스키마 실패/필수 누락/타입 오류
      courseDataMapper.fuzz.test.ts        // 프로퍼티 기반 (경량)
  contract/
    mapper.schema.contract.test.ts         // zod 스키마 ↔ 출력 계약
    supabase.types.contract.test.ts        // 생성된 타입과 호환성 확인
  integration/
    courseDataMapper.db.integration.test.ts // 필수 경로만, in-memory 또는 test DB
  perf/
    courseDataMapper.bench.test.ts         // 대용량 변환 시간 측정 (기본 스킵)
```

## 5) 케이스 샘플 체크리스트

### 금액 로직
- [ ] 정가, 퍼센트 할인, 정액 할인, 세금 순서 규칙 명확화
- [ ] 반올림 규칙(half up/half even) 명시
- [ ] 엣지: 0원, 초고가, 세금 0, 음수 방지

### 입력 정규화
- [ ] 빈 문자열 → null 또는 유지, 규칙 일관성 유지
- [ ] 태그: 트리밍, 중복 제거, 특수문자 허용 범위
- [ ] 날짜: ISO 외 형식 실패 시 오류 또는 기본값, 정책 일관성

### 에러 표준화
- [ ] `ZodError` → 내부 `DomainError` 변환 여부, 코드/필드 경로 노출 정책

### 통합/계약
- [ ] Supabase 생성 타입과 맵퍼 출력 간 호환성 검증
- [ ] 마이그레이션 시 필드 변경 조기 경고

### 비기능
- [ ] 대량 N=100k 변환 95p 지연 < X ms (로컬 기준, CI 스킵)
- [ ] 메모리 피크 < Y MB (선택 사항)

## 6) 스냅샷 대신 명시적 어서션 권장

**권장하지 않음**:
```ts
expect(mapCourse(input)).toMatchSnapshot();
```

**권장**:
```ts
const out = mapCourse(input);
expect(out.price.final).toBe("123.45");        // 문자열 통화 포맷 고정
expect(out.tags).toEqual(expect.arrayContaining(["ai", "무료"]));
expect(out.startsAt).toBe("2025-09-01T00:00:00Z"); // 타임존 포함
```

## 7) 성능 테스트 운용 원칙

- CI에서는 기본 **스킵**. `CI_PERF=1` 환경변수 설정 시에만 실행.
- 실패 기준은 절대값보다 **회귀 탐지** 중심 (이전 대비 +X% 초과 시 경고).
- 성능 테스트는 회귀 검사용이며, 정확성 검증 수단이 아님.

## 8) 커버리지 전략

커버리지 숫자 자체는 품질을 담보하지 않음. **리스크 기반 커버리지**를 목표로:
- 금액·보안·데이터 정합성 관련 코드: 100% 가까이 목표
- 나머지: 적정선 유지

## 결론

### 핵심 원칙
- 에러/엣지/통합을 분리하여 테스트
- 스냅샷 과다 사용 지양
- 성능 테스트는 단위 테스트와 분리
- 커버리지 숫자보다 리스크 기반 접근

### 추가 권장사항
- 런타임 스키마 검증 (Zod)
- 프로퍼티 기반 테스트
- 계약 테스트
- 시간 고정 (fakeTimers)
- 테스트 데이터 빌더
